# The SD card image

The layout is the vendor SDK's, sector for sector
(`OrangePiRK3399_scripts/lib/build_image.sh`). This is not a style choice:
the BootROM looks for the first-stage loader at a fixed offset, and U-Boot
finds its partitions by GPT name and the root filesystem by partition GUID.
These are not free parameters.

All values are 512-byte sectors, and all of them live in `config/board.conf`.

```
sector 64        idbloader.img    raw, inside no partition   (TPL + SPL)
part 1  uboot    24576 – 32767      8 MiB   uboot.img, raw
part 2  trust    32768 – 40959      4 MiB   trust.img,  raw
part 3  boot     49152 – 311295   128 MiB   boot.img,   raw
part 4  rootfs   376832 – …      6144 MiB   ext4
part 5  msd      after rootfs      64 MiB   ext4, grown on first boot
```

## Things that will bite you

**The boot partition is not a filesystem.** There is no `/boot` on the running
board. Partition 3 holds a raw Android boot image built by the Rockchip kernel
Makefile: the kernel `Image` plus `resource.img`, which is where the DTB
lives. Updating a kernel means `dd`-ing a new `boot.img` over partition 3, not
copying a file.

**It is 128 MiB, not the vendor's 32 MiB.** 6.12's `boot.img` is 41 MiB —
`rockchip_linux_defconfig` builds far more in than the vendor's 4.4 config
did. At 32 MiB it is silently truncated and the board fails to boot with no
useful message. Growing it was free: the vendor layout already leaves ~128 MiB
unclaimed between boot and rootfs (their "backup" region), so rootfs still
starts at exactly the sector it always did. `mkimage.sh` hard-fails if
`boot.img` outgrows the partition, so this cannot regress quietly.

**The rootfs is a fixed 6 GB and never grows.** MSD sits behind it, so
widening it after the fact would mean moving another partition. `mkfs.ext4`
gets `-O ^metadata_csum -b 4096`, which is what the vendor kernel and U-Boot
can read.

**Only the MSD partition expands**, on first boot, via
`overlay/usr/lib/pikvm/expand-msd.sh` and `pikvm-expand-msd.service`. It is
last in the table for exactly that reason. So the card size you choose becomes
ISO storage and nothing else.

**The partition GUIDs are functional.** U-Boot's bootargs name the rootfs by
`614e0000-0000-4b53-8000-1d28000054a9`, and `/etc/fstab` names the MSD store
by `…54aa`. `mkimage.sh` sets both explicitly with `sgdisk`. Change them and
the board stops at "rootfs not found".

## /etc/fstab

Generated by `mkimage.sh`, and both lines carry load-bearing options.

```
PARTUUID=…54a9  /                  ext4  defaults,noatime,commit=600  0 1
PARTUUID=…54aa  /var/lib/kvmd/msd  ext4  nodev,nosuid,noexec,ro,errors=remount-ro,\
                                         X-kvmd.otgmsd-root=/var/lib/kvmd/msd,\
                                         X-kvmd.otgmsd-user=kvmd  0 2
```

`commit=600` flushes the ext4 journal every 10 minutes instead of every 5
seconds. It is a wear trade with an explicit cost: an unclean power loss can
lose ten minutes of metadata rather than five. It is the right trade here
because the system writes almost nothing between reboots — the journal is in
RAM, kvmd's runtime state is in `/run` and `/tmp` — so there is rarely ten
minutes of anything to lose. Everything that genuinely matters, i.e. an
uploaded ISO, goes to the MSD partition instead.

**kvmd finds its image store by scanning `/etc/fstab`** for a six-field line
whose options contain `X-kvmd.otgmsd-root=` (`kvmd/fstab.py`). Without that
option the API reports `storage: null` and no ISO can ever be uploaded. The
store is mounted `ro` on purpose: kvmd flips it to `rw` through
`kvmd-helper-otgmsd-remount` only for the duration of a write, so a crash
mid-upload cannot leave it dirty.

## One non-obvious step in mkimage.sh

`rm -f /.dockerenv`. The rootfs comes out of `docker export`, and the
container runtime creates that file in every container it starts, so it is in
the tarball. Leave it and `systemd-detect-virt` answers `docker` on the real
board, systemd skips every unit guarded by
`ConditionVirtualization=!container`, and `systemd-timesyncd` never starts.
The board has no RTC, so nothing ever sets the clock and every log timestamp
stays in 1970. `systemd-random-seed` is skipped for the same reason.

## Rebuilding just the image

`make image` reassembles from what is already in `output/` — the three
bootloader blobs, `boot.img`, and `rootfs.tar` — so changing a partition size
or the fstab is a three-minute rebuild, not a two-hour one.
